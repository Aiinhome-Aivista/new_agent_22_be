MERMAID TOPOLOGY RULES & CANONICAL RUNTIME FLOW
============================================================
The Mermaid diagram represents the canonical runtime topology derived from the source diagram and developer requirements.
It must faithfully preserve:
- every visible node
- every visible edge
- every branch
- every parallel path
- every loop
- every independent failure path

Ensure the Mermaid diagram clearly distinguishes:
- business/runtime topology
- implementation component relationships
- method call/return semantics
- Kafka topic direction
- error routing

Do not add implementation-only classes such as Processor/Supplier/Handler to Mermaid unless:
1. they are explicitly visible in Miro, OR
2. Developer Provided Facts explicitly define them as runtime topology components.
Implementation mappings should normally be described in class_design and implementation_contract.

When implementation components (such as Processor, Supplier, Handler) ARE explicitly defined as runtime topology components, you MUST adhere to the following rules:

1. PROCESSOR UNIQUENESS RULE:
- Prevent the same logical Processor component from appearing multiple times in the canonical Mermaid runtime topology.
- When Processor, Supplier, and Handler are implementation components of one processing pipeline, represent each logical component only once.
- For example, if the implementation contract is:
  Input Topic → Processor → Supplier → Handler → AvroOutput → Output Topic
  the Mermaid topology MUST NOT become:
  Input Topic → Processor → Supplier → Handler → Processor → Output Topic
  The second Processor is incorrect if it represents the same logical Processor component receiving the Handler result before publishing.
- A single Processor may perform all of the following responsibilities:
  * consume/read the input event
  * invoke the Supplier
  * receive the Supplier/Handler result
  * publish the successful output
  * route failures/errors to the configured error destination
- Therefore, represent the Processor only once in the topology.
- Correct conceptual representation:
  Input Topic
  ↓
  Processor
  ↓
  Supplier
  ↓
  Handler
  ↓
  Output Topic
  with an error branch:
  Processor
  ↓
  Error Topic
- Do not create duplicate nodes merely because control returns to the Processor after Supplier/Handler execution.
- This rule applies only when the nodes represent the same logical implementation component. If the Developer Input or Miro Diagram explicitly defines two genuinely different Processor components, preserve both and distinguish them clearly (e.g., IngestionProcessor and DownstreamProcessor).

2. ERROR FLOW DIRECTION RULE:
- Add an explicit topology-direction rule for error handling: Errors must ALWAYS flow FROM the component detecting/routing the error TO the configured error destination.
- For example:
  Processor → Error Topic  (CORRECT)
  Error Topic → Processor  (INCORRECT: DO NOT REVERSE ARROWS)
- Do NOT reverse error-flow arrows.
- If the Processor validates or processes an event and determines that it must be rejected or routed to an error flow, the canonical topology must represent:
  Input Topic
  ↓
  Processor
  ├── success → Supplier → Handler → Output Topic
  │
  └── error → Error Topic
- The Error Topic must NOT be shown as an input to the same Processor unless Developer Input or Miro Diagram explicitly defines a separate error-consumption workflow.
- Important: Do not infer an error-consumer workflow merely because an error topic exists. An error topic is an output destination when the processing component publishes an error event to it.

3. DISTINGUISH ERROR DESTINATION FROM ERROR CONSUMER:
- An error topic must not automatically be treated as an input topic.
- The existence of "Error Topic" does NOT imply "Error Topic → Processor".
- Determine the direction strictly from Developer Input and Miro Diagram facts:
  * If the documented behavior is "route errors", "publish errors", "send failures", "reject and publish", or equivalent, represent:
    Processor → Error Topic
  * Only represent "Error Topic → Error Processor" when the Developer Input or Miro Diagram explicitly defines a downstream consumer/processor for that error topic.
  * Do not invent an error consumer.

4. TOPOLOGY VALIDATION CHECKLIST:
Before producing the final Blueprint, internally validate the generated Mermaid topology against these rules:
A. Every arrow must represent the actual runtime direction.
B. Error routes must point toward the error destination (e.g., Processor → Error Topic).
C. The same logical component must not be duplicated unless the source architecture explicitly defines multiple instances/components.
D. A topic must not automatically become an input merely because it is named as an error topic.
E. Do not invent consumers, processors, handlers, services, topics, or components.
F. Mermaid topology must represent runtime behavior, not merely class call/return semantics.
G. A method call returning to its caller must NOT be represented as a second instance of the caller.
   For example:
   Processor calls Supplier.
   Supplier calls Handler.
   Handler returns a result.
   Supplier returns the result to Processor.
   This is a control-flow/call-return relationship, NOT:
   Processor → Supplier → Handler → Processor
   The canonical topology should represent the logical processing pipeline without duplicating the Processor node.

5. TOPOLOGY PATTERN ENFORCEMENT SUMMARY:
Most importantly, the final Mermaid topology must prevent these two incorrect outputs:
- INCORRECT:
  Error Topic → Processor
- INCORRECT:
  Processor → Supplier → Handler → Processor → Output Topic

And it must correctly support:
- CORRECT:
  Input Topic → Processor → Supplier → Handler → Output Topic
- CORRECT:
  Processor → Error Topic

while still allowing genuinely separate processors/components when they are explicitly defined by the Developer Input or Miro Diagram.
